# 앱 재시작 후 상태 복구(중계 프로세스) 설계

- 날짜: 2026-11-22
- 담당: A(실행 제어)
- 브랜치: `feat/runner`
- 이슈: #28(FR-11, AT-06·07). #29(FR-12 "계속 실행")의 바탕이 된다.

## 목적

포폴링은 "어떤 포트를 어떤 프로젝트가 쓰는지" 보여 주는 앱이다. 앱이 꺼져도 실행해 둔 서비스는 계속 돌아야 하고, 앱을 다시 켜면 그 서비스를 되찾아 `실행 중`·포트 주인·[중지]를 다시 보여 줘야 한다(사용자 결정).

## 지금의 문제 (2026-11-22 실험)

서비스 출력은 파이프로 앱이 직접 받는다. 앱이 강제 종료되면 파이프의 읽는 쪽이 사라지고, 서비스는 다음 줄을 쓰는 순간 죽는다.

| 서비스 (macOS, 실제 실행 방식과 같게 `perl setpgrp`로 띄움) | 부모를 `kill -9` 하고 3초 뒤 |
|---|---|
| Node `console.log` 0.3초마다 | 죽음 |
| Python `print` 0.3초마다 | 죽음 |
| Node `console.error` 0.3초마다 | 죽음 |
| `sleep 600`(출력 없음) | 살아 있음 |

그래서 복구 기능만 붙이면 대부분 되살릴 게 남지 않는다. 출력을 앱 대신 받아 줄 프로그램이 서비스 옆에 있어야 한다.

## 방식 비교

| 방식 | 장단점 |
|---|---|
| **1. Dart 중계 프로그램 (선택)** | 중계를 Dart로 한 번 짜서 OS별 실행 파일로 만들어 앱에 넣는다. 두 OS가 코드 하나이고, 비밀값 가리기·회전을 `LogStore`의 Dart 코드에서 옮겨 쓴다. 빌드 때 중계를 만들어 넣는 단계가 생긴다 |
| 2. OS별 스크립트(macOS `perl`, Windows PowerShell) | 빌드 단계는 없지만 같은 규칙을 Dart·perl·PowerShell 세 곳에서 관리한다. PowerShell은 시작이 느리고 무겁다 |
| 3. 서비스 출력을 파일로 바로 보내기(중계 없음) | `.env` 값이 가려지지 않은 채 파일에 쌓이고(규칙 위반), 10MB 회전을 할 주체가 없다 |
| 4. 지금 방식 유지 | 앱이 꺼지면 서비스도 사실상 끝난다. #29 "계속 실행"을 지킬 수 없다 |

중계가 앱에 넘기는 방법도 둘이었다: (a) 파일에 쓰면서 앱에도 그대로 전달, (b) 파일에만 쓰고 앱은 파일을 읽기. **(a)를 고른다(구현자 판단).** 준비 확인(`log` 조건)과 오케스트레이터 흐름을 그대로 두고, 앱이 꺼지면 전달만 멈추면 된다. (b)는 준비 확인까지 파일 폴링으로 바꿔야 해서 오케스트레이터를 크게 고친다.

## 정한 것

### 동작
1. **앱이 꺼져도 서비스는 계속 돈다.** 직접 닫든(#29에서 "계속 실행"을 고른 경우) 갑자기 꺼지든 같다. macOS·Windows 둘 다(사용자 결정).
2. **앱을 다시 켜면** 실행 기록(`runtime.json`)의 프로세스마다 소유권을 확인한다.
   - 증명됨 → `실행 중`으로 되살리고 [중지]·포트 주인 판단(`RuntimeQuery`)이 다시 된다. 준비 조건이 `http`·`port`면 한 번 확인해 통과하면 `준비 완료`.
   - 살아 있지만 증명 안 됨 → `확인 불가`. 멈추지 않고 [중지]도 주지 않는다(AT-07, FR-11).
   - 죽었음 → 기록만 지운다. 상태는 `중지`.
3. **Compose 항목도 되살린다(사용자 결정).** 앱 시작 때 각 프로젝트의 Compose 항목을 `ItemLauncher.status`로 물어, 컨테이너가 떠 있으면 `실행 중`. Compose는 원래 앱과 상관없이 Docker가 돌리므로 중계가 필요 없다.
4. **로그:** 중계가 계속 파일에 쓰므로 재시작 뒤에도 항목 상세 화면(이미 1초마다 파일을 읽음)에 로그가 이어진다.

### 중계 프로그램(`popoling-relay`)
5. **하는 일:** 서비스를 띄우고, stdout·stderr를 줄 단위로 받아 ① `.env` 값을 `****`로 가리고 ② `<ISO 시각> out|err | 내용` 형식으로 로그 파일에 쓰고(10MB×3 회전, 시작 구분 줄 포함 — 지금 `LogStore` 형식 그대로) ③ 같은 줄(가린 것)을 자기 stdout·stderr로 앱에 넘긴다.
6. **앱이 꺼졌을 때:** 앱 쪽 전달이 실패하면(파이프 끊김) 전달만 그만두고 파일 쓰기는 계속한다. 끊긴 파이프 때문에 중계가 죽으면 안 된다.
7. **수명:** 서비스와 그 자식이 출력을 모두 닫고 서비스가 끝나면 중계도 끝난다. 종료 코드는 서비스의 종료 코드를 그대로 쓰고, 로그 끝에 `--- 끝 (종료 코드 N) ---`을 남긴다(재시작 뒤 되살린 항목이 끝났을 때 결과를 알기 위해).
8. **비밀값 전달:** `.env` 값은 명령 인자로 넘기지 않는다(프로세스 목록에서 누구나 본다). 중계의 stdin으로 넘기고, 서비스의 stdin은 지금처럼 바로 닫는다.
9. **멈추는 신호:** macOS에서 앱이 그룹 전체에 TERM을 보내면 중계는 TERM을 무시하고 서비스가 남긴 마지막 출력까지 받아 적은 뒤 끝난다. KILL이면 모두 끝난다.
10. **패키지:** Flutter에 기대지 않는 순수 Dart 패키지로 `runner/relay/`에 둔다(`dart compile exe`가 Flutter 패키지를 다루지 못할 수 있어서). 가리기·회전·줄 형식 코드는 이 패키지로 옮기고 `runner`가 가져다 쓴다(Windows 기존 경로·`LogStore.tail`·`LogExcerpt`가 같은 형식을 쓰도록).

### OS별 소유권과 멈추기
11. **macOS:** 중계가 새 프로세스 그룹을 만든다(FFI `setpgid`, 지금의 `perl setpgrp` 대신). 중계는 서비스가 끝날 때까지 살아 있으므로, 재시작 때 **중계 PID가 살아 있고, 그 프로세스의 그룹이 자기 자신이고, 실행 파일이 `popoling-relay`이고, 시작 시각이 기록과 2초 안에서 같으면** 내가 띄운 것이다. 지금 생기는 "첫 프로세스만 끝나고 자식만 남아 증명 불가" 문제도 사라진다. 멈추기는 지금처럼 그룹 전체 TERM → 시간 초과 시 KILL.
12. **Windows:** Job에 이름을 붙인다(`popoling-<기록 ID>`). 앱이 이름 붙은 Job을 만들어 중계를 넣고, 중계도 같은 이름으로 Job 핸들을 하나 열어 둔다. 이름 붙은 객체는 핸들이 모두 닫히면 이름으로 찾을 수 없게 되므로, 앱이 꺼져도 중계가 핸들을 쥐고 있어야 다시 열 수 있다. 재시작 때 **이름으로 Job을 열 수 있고 그 안에 기록된 중계 PID가 들어 있으면** 내가 띄운 것이다. 멈추기는 지금처럼 Job째 강제 종료.
13. **기록 형식:** `ProcessRecord`에 Windows Job 이름을 더한다. 기존 `runtime.json`(이름 없음)을 읽어도 깨지지 않아야 한다(없으면 Windows에서 `확인 불가`).

### 빌드
14. 앱 빌드 때 중계를 만들어 넣는다. macOS는 Xcode 빌드 단계에서 `dart compile exe`로 만들어 앱 번들 안에, Windows는 CMake 단계에서 만들어 실행 파일 옆에 둔다. `flutter run`·`flutter build`·CI 빌드 모두 이 단계를 거친다. 앱은 실행 중 자기 실행 파일 위치(`Platform.resolvedExecutable`) 기준으로 중계를 찾는다.
15. runner 테스트는 시작할 때 한 번 중계를 컴파일해서 쓴다. Windows 동작은 기존처럼 CI의 `runner-windows` job으로 확인한다(팀에 Windows 기기 없음).

## 목표가 아닌 것

- 정상 종료 신호로 멈추기(Windows): 지금처럼 Job째 강제 종료.
- #29 앱 종료 확인 창: 이번에는 바탕만 만들고, 창은 #29에서.
- 되살린 항목의 재시작 전 화면 버퍼: 로그는 파일에서 읽는다.
- 삭제한 프로젝트의 남은 프로세스 정리 화면.

## 실패로 보는 것 (동작은 해도 안 되는 것)

- 증명이 안 된 프로세스를 멈추거나 [중지] 버튼을 주는 것.
- `.env` 값이 로그 파일·화면·프로세스 목록(명령 인자)에 평문으로 나타나는 것.
- 중계가 죽어서 서비스가 따라 죽는 것(끊긴 파이프, 로그 쓰기 실패 등).

## 확인하지 못한 것 (구현하며 먼저 검증)

- Windows에서 이름 붙은 Job을 중계가 핸들로 쥐고 있으면 앱이 꺼진 뒤에도 이름으로 다시 열리는지 — CI에서 먼저 시험한다. 안 되면 대안: 중계 PID + 생성 시각(`GetProcessTimes`)으로 증명하고, 멈추기는 중계에게 요청한다.
- Xcode·CMake 빌드 단계에서 Flutter에 들어 있는 `dart`로 `dart compile exe`가 되는지, CI 빌드 시간이 얼마나 늘어나는지.
- 중계 하나당 메모리(항목 20개일 때 합계) — 5주차 성능 확인(#47)에서 잰다.

## 바뀌는 파일 (예상)

- 새로 만듦: `runner/relay/`(중계 프로그램·가리기·회전·줄 형식), 복구 테스트
- 수정: `runner/lib/src/process/`(macOS·Windows 실행기, Windows Job 이름), `runner/lib/src/runtime/runtime_store.dart`(기록 형식), `runner/lib/src/orchestrator/runner_orchestrator.dart`(앱 시작 때 복구), `runner/lib/src/log/log_store.dart`(형식 코드를 relay 패키지로), `runner/lib/runner.dart`(시작 때 복구 호출), `app/macos/Runner.xcodeproj`·`app/windows/CMakeLists.txt`(중계 빌드), `.github/workflows/ci.yml`(필요하면)
- `core/`는 바꾸지 않는다(`ItemState.unknown`·`ItemLauncher.status`가 이미 있다).
