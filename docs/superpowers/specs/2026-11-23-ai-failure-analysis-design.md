# AI-02 실행 실패 원인 분석 설계

- 날짜: 2026-11-23
- 담당: D(`ai/`). 쓰는 계약: `Orchestrator`·`LogExcerpt`(A), `EnvDiff`(C, 아직 앱에 등록 안 됨), `ProjectRepository`(B), `LlmClient`(D)
- 브랜치: `feat/ai-failure-analysis` · 이슈 #42
- 기준: 기획서 §2 AI-02 줄·원칙·완료 기준, AT-19·21·22, 화면 문구 초안 §4 "실행 실패 원인 분석 카드"·§6 "보내기 전 확인"

## 목적

실행이 실패하면 터미널이 익숙하지 않은 사람은 로그만 보고 원인을 찾기 어렵다. [원인 분석]을 누르면 실패한 항목의 실패 이유·실행 설정·로그 끝부분·마지막 성공 때와 달라진 환경을 Gemini에 보내고, 원인 후보(가능성 높음/있음)와 해결 방법을 받는다. 후보마다 근거(로그 줄, 환경 차이, 실패 이유)를 앱이 가진 실제 값으로 보여준다.

## 목표 · 하지 않는 것

- 목표
  - 마지막 전체 실행에서 실패한 항목마다 [원인 분석]을 둔다.
  - 원인 후보를 하나 이상 보여주고(완료 기준), 후보마다 근거와 해결 방법을 붙인다.
  - AT-22: Node를 20 → 22로 바꿔 실행이 실패하면 후보에 환경 변화("node 20.11.0 → 22.3.0")와 근거 로그 줄이 나온다.
  - `EnvDiff`가 앱에 없어도 화면이 열리고 로그만으로 분석한다(일정 문서 4주차: "수요일까지 `EnvDiff`가 안 붙으면 로그만으로 분석").
  - [보내기]를 누르기 전에는 요청 0건. 보낸 내용에 `.env` 값·환경변수 값·API 키·호스트가 없다(AT-21).
  - AI-02·AI-03이 같이 쓰는 "보내기 과정"을 `ai/` 안 공통 조각 하나로 모은다. #43 분석 기록을 한 곳에서 남기기 위해서.
- 하지 않는 것
  - 항목 하나만 [시작]해서 실패한 경우. `lastRun`에 남지 않고 이유도 저장되지 않는다.
  - 분석 기록 저장(#43, 4주차 후반). 이번엔 공통 조각에 기록할 자리만 생긴다.
  - 화면 6(헬스체크 결과, C)·화면 2 오래된 프로젝트 점검(FR-17)의 [원인 분석] 버튼. 패널만 내보내 둔다.
  - [환경 점검 보기]·[전체 로그] 버튼(문구 초안에 있음). 이동할 화면(C의 `/env`, A의 `/detail`)이 아직 어느 항목인지 넘겨받지 못한다.
  - `core/`·`app/`·다른 기능 패키지 변경.
- 실패로 보는 것
  - AI가 지어낸 로그 줄이나 버전이 근거 칸에 나오는 것.
  - 환경변수 값이나 `.env` 내용이 보낼 내용에 섞이는 것.
  - `EnvDiff`가 없다고 화면이 오류로 멈추는 것.
  - AI-03 동작이 바뀌는 것.

## 방식 비교

### 분석 대상 (수연 결정: 항목마다)

| 방식 | 내용 | 장단점 |
|---|---|---|
| **항목마다 따로 (선택)** | 실패한 항목마다 [원인 분석] | 보내는 로그가 한 항목 것이라 짧고 근거가 섞이지 않는다. 문구 초안 "{항목} · {어제} 실패"와 맞다 |
| 한 번에 묶어서 | 실패 항목을 모두 한 번에 | 사용량 1회, 항목 사이 관계를 볼 수 있지만 내용이 길고 근거가 섞인다 |
| 첫 실패 하나만 | 자동으로 하나 | 가장 단순하지만 다른 실패는 분석할 수 없다 |

### 보낼 내용 (수연 결정: 실행 설정 포함)

기획서의 "실패 로그 일부, 환경 비교 결과"에 **항목 실행 설정**(명령·폴더·포트·준비 조건)을 더한다. "명령이 틀림", "포트가 다름" 같은 원인을 맞힐 수 있게. 환경변수 값과 `.env` 내용은 넣지 않는다. 기획서 §2 AI-02 줄도 이번 PR에서 고친다(아래 7).

### 코드 구조 (수연 결정: 공통 부분 빼서 같이 쓰기)

| 방식 | 내용 | 장단점 |
|---|---|---|
| 1. AI-02 패널 따로 | AI-03 코드는 그대로, 같은 흐름을 새 패널에 한 번 더 | 빠르지만 약 110줄이 두 곳에. 분석 기록도 두 곳에서 남겨야 한다 |
| **2. 공통 조각 + 두 패널 (선택)** | 키 확인·확인 창·분석 중/취소·늦은 답 버리기·오류 안내를 `ai/` 공통 조각으로, 두 패널은 "보낼 글"과 "결과 그리기"만 | AI-03 코드를 고쳐야 한다(기존 테스트로 확인). #43 기록·화면 6·FR-17에 같은 조각을 쓴다 |
| 3. AI-03 패널에 AI-02 모드 | 위젯 하나가 둘 다 | 위젯 하나가 두 역할을 맡아 뺐다 |

## 설계

### 1. 분석할 실패 찾기

- `Orchestrator.lastRun(projectId)`의 `items`를 처리 순서 그대로 보여준다.
  - `failed`: `{항목} · 실패 · {이유}`와 [원인 분석]. 이유가 없으면 `종료 코드 {n}`, 그것도 없으면 `이유를 알 수 없어요`.
  - `skipped`: `{항목} · 건너뜀 · {이유}`, 버튼 없음. 시작하지 않아 로그가 없다.
  - `ok`: 보여주지 않는다.
- 카드 머리: `{오늘 14:00 | 11/20 14:00} 전체 실행 기준`(`finishedAt`). 헬스체크 카드의 "검사 기준"과 같은 모양을 쓴다(같은 화면에서 "어제"와 "11/22"가 섞이지 않게).
- 실패한 항목이 없거나 `lastRun`이 null: "실패한 실행이 없어요. 실행이 실패하면 여기서 원인을 찾아 드려요."
- `lastRun`을 못 읽으면(예외): 같은 빈 문구를 보여준다. (내 결정: 따로 오류 문구를 만들 만큼 흔하지 않다.)
- 화면을 열 때 한 번 읽는다. 열려 있는 동안 새로 실패해도 바로 바뀌지 않는다. (내 결정)

### 2. 보낼 글 `ai/lib/src/failure_analysis.dart` (화면 없음)

[원인 분석]을 누를 때마다 새로 만든다(로그를 그때 읽는다). 근거를 번호로 고르게 하려고 번호를 붙인다.

```
[실패한 항목] api · 내 컴퓨터에서 실행 · 11/22 14:00 전체 실행
#R 시작하자마자 종료됐어요 (종료 코드 1).
[실행 설정] 명령 npm run dev · 폴더 ./backend · 포트 8080 · .env 파일 씀(내용은 보내지 않음)
  준비 조건 HTTP /actuator/health 응답(60초 안) · 먼저 떠야 하는 항목 db
[같은 실행의 다른 항목] db 성공 · web 건너뜀(api가 실패해서)
[환경 차이] 마지막 성공 실행과 비교
#E1 node 20.11.0 → 22.3.0
[로그] api 마지막 50줄
#L1 > backend@1.0.0 dev
#L2 Error: The module was compiled against a different Node.js version
```

- **실패 이유(#R):** `ItemResult.reason`. `exitCode`가 있고 이유에 "종료 코드"가 없으면 `· 종료 코드 {n}`을 붙인다. 둘 다 없으면 "이유를 알 수 없어요".
- **항목 종류:** `process` 내 컴퓨터에서 실행 · `compose` Docker Compose · `remote` 원격 연결.
- **실행 설정** (`ProjectRepository.getProject(id).config.services`에서 같은 id)
  - `process`: 명령(인자를 공백으로 잇고, 공백이 든 인자는 따옴표), 폴더(`cwd`, 프로젝트 기준 상대 경로 그대로), 포트, `envFile`이 있으면 ".env 파일 씀(내용은 보내지 않음)". **`env`(환경변수)는 이름도 값도 보내지 않는다.** (내 결정: 값에 비밀이 섞일 수 있어 가장 안전한 쪽)
  - `compose`: compose 파일, 서비스 이름(비면 "파일 전체").
  - `remote`: 준비 조건만.
  - 준비 조건: `HTTP {경로} 응답` (+ `코드 {n}` 기대값이 있으면) · `포트 {n} 연결` · `로그에 "{정규식}"` · `compose healthy` · 없음. 뒤에 `({timeout}초 안)`. 주소는 AI-03의 `stripHost`로 호스트를 뺀다. `PortReady.host`는 보내지 않는다.
  - 설정에서 그 항목을 못 찾으면: "설정에서 이 항목을 찾지 못했어요."
- **같은 실행의 다른 항목:** `lastRun`의 나머지 항목 `{id} {성공|실패|건너뜀}(이유)`. 의존 관계로 생긴 실패를 보게.
- **환경 차이** (`EnvDiff.sinceLastSuccess`)
  - `EnvDiff`가 앱에 없음·예외: "환경 비교를 아직 쓸 수 없어요."
  - null: "마지막 성공 실행 기록이 없어요."
  - 빈 목록: "마지막 성공 실행과 달라진 것이 없어요."
  - 있음: `#E{n} {이름} {before} → {after}`. before/after가 null이면 `없음`.
- **로그** (`LogExcerpt.tail(projectId, serviceId, lines: 50)`, `.env` 값은 A가 이미 가렸다)
  - 한 줄이 300자를 넘으면 자르고 `…`. (내 결정: 확인 창에서 읽을 수 있게)
  - 빈 목록: "남은 로그가 없어요." · `LogExcerpt`가 없음·예외: "로그를 읽지 못했어요."
- 보내기는 `AiSender.send(requestName: '실행 실패 원인 분석', notes: ['실행 설정은 명령·폴더·포트·준비 조건만 보내요. 환경변수와 .env 파일 내용은 보내지 않아요.'])`. 확인 창의 "비밀값으로 보이는 n곳을 가렸어요"는 `AiSender`가 이미 붙인다.

### 3. AI 지시와 답 읽기

**지시(system).** 실행 실패 원인 분석 도우미. 터미널을 잘 모르는 사람도 알아들을 쉬운 한국어 존댓말. 원인 후보 1~3개를 가능성 높은 순으로. 후보마다 원인 한두 문장, 가능성(`high`/`possible`), 근거 번호, 사용자가 직접 할 수 있는 해결 방법 1~4단계(명령이 필요하면 그대로 칠 명령). 로그·설정·환경에 없는 값을 지어내지 않는다. 데이터를 지우는 명령(예: `rm -rf`, `docker compose down -v`)은 제안하지 않고, 꼭 필요하면 무엇이 지워지는지 먼저 말한다. 답은 JSON 하나만:

```json
{"candidates":[{"cause":"Node 버전이 바뀌어 설치된 모듈이 맞지 않아요.","likelihood":"high","logs":[2],"env":[1],"reason":false,"fixes":["backend 폴더에서 npm install 을 다시 해 주세요.","또는 Node 20으로 되돌려 주세요."]}]}
```

**답 읽기.**

- AI-03처럼 첫 `{`부터 마지막 `}`까지 읽는다(울타리 무시).
- `cause`가 빈 후보는 뺀다. `likelihood`가 `high`면 "가능성 높음", 그 밖은 "가능성 있음".
- `logs`·`env` 번호 중 이번 글에 없는 번호는 무시한다. `reason: true`면 실패 이유(#R)가 근거다.
- 남은 근거가 하나도 없는 후보는 뺀다. "근거와 함께"가 원칙이라서.
- `fixes`는 빈 문자열을 빼고 앞 4개까지. 후보는 앞 3개까지, 가능성 높음을 앞으로(같은 가능성끼리는 AI 순서).
- 남는 후보가 없거나 JSON이 아니면 "AI 답을 읽지 못했어요." · [다시 분석].
- 근거 칸은 앱이 실제 데이터로 만든다.
  - `근거 로그 · {항목} 마지막 실행` 아래에 고른 번호의 실제 줄(고정폭 글꼴)
  - `환경 차이 · node 20.11.0 → 22.3.0`
  - `실패 이유 · {이유}`

### 4. 보내기 공통 조각 `ai/lib/src/ai_request.dart`

AI-03 패널(`qa_summary_panel.dart`)에서 아래를 옮긴다.

- 키 확인(`isConfigured`, 못 읽으면 "보안 저장소" 상태)
- `AiSender`로 보내기, 보낼 때마다 번호를 올려 [취소]·화면 떠남 뒤의 답 버리기
- 상태와 그 화면: 분석 중 + [취소] · 취소함 · 오류 4종(`llmErrorText`와 그 버튼) · 키 저장소 못 읽음 + [다시 시도] · 답 못 읽음 + [다시 …]
- [키 입력] 창 열기와 `onKeysChanged`

각 패널이 넘기는 것: 분석 이름, 보낼 글(보낼 때 만드는 비동기 함수), 지시, 안내(notes), 답 읽기(못 읽으면 null), 시작 버튼 이름(AI 요약/원인 분석), 다시 버튼 이름(다시 요약/다시 분석), 완료 화면 그리기.

- AI-03의 "검사할 항목이 없어요"·"모든 검사를 통과했어요"(API 안 부름)는 공통 조각 앞에서 `QaSummaryPanel`이 그대로 처리한다.
- 조각의 모양(위젯+builder인지, 상태 객체인지)은 구현 계획에서 정한다.
- **AI-03 동작은 바뀌지 않는다.** `qa_summary_panel_test.dart`는 고치지 않고 통과해야 한다.
- #43에서 이 조각에 "분석이 끝날 때(완료·실패·취소) 기록"을 더한다. 이번엔 넣지 않는다.

### 5. 원인 분석 패널 `ai/lib/src/failure_analysis_panel.dart`

`FailureAnalysisPanel(item, run, ...)`. `ai.dart`에서 내보낸다(화면 6·FR-17에서 쓰려고). 필요한 것(`LlmClient`, `ApiKeyStore`, `ProjectRepository`, `LogExcerpt?`, `EnvDiff?`)은 생성자로 받는다.

| 상태 | 보이는 것 |
|---|---|
| 처음 | [원인 분석] (설명 문구는 카드에 한 번만) |
| 키 없음 | "API 키 필요" 안내 · [키 입력] (AT-19) |
| 분석 중 / 취소함 / 오류 / 키 저장소 / 답 못 읽음 | 공통 조각 그대로. 다시 버튼은 [다시 분석] |
| 완료 | 후보마다 `원인 후보 · 가능성 높음`(라벨, 색만으로 나누지 않음), 원인 문장, 근거 칸들, `해결 방법` 번호 목록 · "분석 완료 · {모델 이름}" · "AI 결과는 틀릴 수 있어요. 근거(로그 줄, 검사 항목)를 확인한 뒤 판단해 주세요." · [다시 분석] |
