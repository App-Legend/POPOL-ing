# 포폴링(PPOL-ing) — 역할 분담

**인원:** 4명  
**기준 문서:** `docs/포폴링_개발기획서.md`, `docs/포폴링_6주_개발일정.md`

원칙: **기능 단위로 나눈다.** 한 사람이 맡은 기능의 화면·로직·테스트를 끝까지 책임진다. 폴더 하나에 주인은 한 명이고, 기능끼리는 `core/`의 인터페이스·이벤트로만 주고받는다.

## 2. 기능 사이 연결

| 제공하는 쪽 | 계약 | 쓰는 쪽 |
|---|---|---|
| A `runner` | `Orchestrator`(전체 실행·종료), `RuntimeQuery`(이 포트를 내 항목이 쓰는지), 이벤트 `ItemStateChanged`·`RunSucceeded` | C 포트 확인·환경 기록, D 카탈로그(마지막 실행)·오래된 프로젝트 점검 |
| B `project` (계약·가짜 구현은 D) | `ProjectRepository`(프로젝트·설정 읽기/쓰기), `ConfigValidator` | A, C, D |
| C `checks`·`compose` | `PortProbe`, `HttpProbe`, `EnvChecker`, `ItemLauncher`(Compose·원격 구현) | A 준비 확인·실행, D QA·오래된 프로젝트 점검 |
| D `catalog`·`qa` | `QaRunner`, 카탈로그 위젯 | `app/`(화면 조립) |

2주차에 `core/contracts`를 확정할 때 이름은 바뀔 수 있다.

## 3. 간섭을 막는 규칙

1. **import:** 각 기능 폴더는 `core/`만 import한다. 다른 기능 폴더를 직접 import하면 CI가 실패시킨다.
2. **같은 일은 한 곳에서:** 포트·HTTP 확인은 C가 만들고, 실행 준비 확인(A)과 QA(D)는 그 계약을 부른다.
3. **여러 기능이 모이는 화면(대시보드):** 각 기능은 위젯을 내보내고 배치는 `app/`에서 A가 한다. 각 기능은 `register()` 함수 하나만 내보낸다.
4. **공통 UI 부품(`core/ui`):** 2주차에 함께 만든다. 이후 추가·변경은 PR로 올리고 다른 사람 1명 이상이 승인한다.
5. **기다리지 않기:** 남의 기능이 끝나기 전에는 `core/fakes`의 가짜 구현으로 개발한다.
6. **`core/` 변경:** 1.0 태그(2주차 금) 이후로는 기존 인터페이스를 고치지 않고 추가만 한다. 꼭 고쳐야 하면 먼저 묻는다.
7. **조립 때 깨지면:** 그 인터페이스를 제공한 사람이 고친다.
8. **브랜치:** `feat/<기능명>` (예: `feat/runner`, `feat/project-settings`, `feat/port-check`, `feat/catalog`)
