# 포폴링(POPOL-ing) — 개발 기획서

**문서 상태:** v1.2  
**저장소:** [App-Legend/POPOL-ing](https://github.com/App-Legend/POPOL-ing)  
**기준 자료:** 프로젝트 통합 관리 도구 발표자료(2026.11), 기획서 초안 v0.1  
**이름의 뜻:** 포트폴리오의 줄임말 '포폴' + 진행 중을 뜻하는 '-ing'. 분야와 상관없이 내 포트폴리오가 지금도 살아 있고 계속 쌓여 가는 상태를 한곳에서 본다는 의미.  
**한 줄 소개:** 개발·디자인·투자 등 분야별 포트폴리오를 카테고리로 나눠 한곳에서 관리하는 통합 포트폴리오 앱. 첫 카테고리는 **개발**로, 내 프로젝트가 무엇이 있는지 한눈에 보고, 바로 실행하고, 계속 실행 가능한 상태로 관리한다.

> 기술 스택은 **Flutter 데스크톱**으로 확정했다. 발표자료의 Riverpod, Markdown 저장 등 나머지 제안 기술은 확정 결정으로 보지 않는다. AI 프로젝트 검사는 **Gemini API**로 MVP에 넣는다. MVP에는 실행 실패 원인 분석(AI-02)과 QA 결과 요약(AI-03)만 넣고, 나머지와 로컬 LLM 전환은 MVP 직후로 둔다(§2 'AI 프로젝트 검사').

## 1. 제품 비전 — 분야 통합 포트폴리오

포트폴리오는 개발자만 준비하는 것이 아니다. 디자이너는 작업물과 작업 과정을, 투자자는 보유 종목과 매매 기록·수익률을, 다른 분야도 각자의 결과물을 모아 정리한다. 어느 분야든 "쌓이면 관리가 안 되고, 시간이 지나면 무엇이었는지 잊고, 필요할 때 바로 꺼내 보여주기 어렵다"는 문제는 같다.

포폴링의 장기 목표는 **분야별 포트폴리오를 카테고리로 나눠 한 앱에서 관리하는 것**이다.

```
첫 화면: 카테고리 선택
 ├─ 개발      ← MVP (이 기획서의 본문 범위)
 ├─ 디자인    ← 후속
 ├─ 투자      ← 후속
 └─ (추가 예정)
```


| 카테고리 | 포트폴리오 항목 예             | 카테고리 고유 기능 예 (구상)                |
| ---- | ---------------------- | -------------------------------- |
| 개발   | 로컬 프로젝트 폴더             | 실행·종료, 환경 점검, 로그, 헬스체크 (§2\~ 본문) |
| 디자인  | 작업물(이미지, Figma 링크, 영상) | 작업물 갤러리, 버전·작업 과정 기록, 내보내기       |
| 투자   | 보유 종목·매매 기록            | 매매 일지, 수익률 추적, 투자 근거 기록          |


**모든 카테고리가 공유하는 공통 코어**

- 포트폴리오 항목 목록(카탈로그), 검색·태그·정렬
- 항목 소개(제목, 한 줄 설명, 링크, 메모, 기간)
- 마지막 활동일과 "오래됨" 표시
- 항목 상세 화면의 기본 틀

**원칙**

- 이 기획서의 기능 요구사항·화면·테스트는 **개발 카테고리**를 다룬다. 다른 카테고리는 별도 기획서로 정의한다.
- 공통 코어는 개발 카테고리에서 실제로 쓰는 것만 만든다. 다른 카테고리를 위해 미리 일반화하지 않고, 두 번째 카테고리를 만들 때 공통 부분을 추출한다.
- 단, 첫 화면 카테고리 선택과 "프로젝트가 어느 카테고리에 속하는지"는 처음부터 데이터에 둔다. 나중에 바꾸기 어려운 부분이기 때문이다.

## 1-1. 개발 카테고리 배경과 문제

프로젝트가 쌓일수록 관리가 어려워진다. 수업 과제, 팀 프로젝트, 사이드 프로젝트가 늘어나면 몇 달 전에 만든 프로젝트는 손을 놓게 된다. 다시 열어 보려 할 때는 다음 문제가 한꺼번에 생긴다.

- **무슨 프로젝트였는지 기억나지 않는다.** 폴더 이름만 봐서는 어떤 목적이었는지, 어떤 기술로 만들었는지 알 수 없다.
- **실행 방법을 잊는다.** 어떤 명령을 어떤 순서로, 어느 폴더에서 입력해야 하는지, DB를 먼저 띄워야 하는지 기억나지 않는다.
- **시간이 지나면 실행되지 않는다.** Node·Java·Docker 이미지 등의 버전이 바뀌어 예전에는 되던 프로젝트가 실행되지 않는다. 무엇이 바뀌었는지 알 근거도 없다.
- **내 프로젝트 전체를 볼 곳이 없다.** 프로젝트가 여러 폴더에 흩어져 있어 무엇이 있는지 한눈에 파악할 수 없다.

포폴링은 **내 프로젝트가 무엇이 있는지 한눈에 보고, 바로 실행하고, 계속 실행 가능한 상태로 관리하는** 데스크톱 앱이다. 프로젝트마다 설명·기술 스택·실행 방법·마지막으로 성공한 실행 환경을 기록해 두므로, 오래된 프로젝트도 다시 열었을 때 무엇이었는지, 어떻게 실행하는지, 왜 실행되지 않는지 알 수 있다.

실행할 때의 번거로움도 함께 줄인다. 개발자는 DB, 백엔드, 프론트엔드, Docker 등의 명령을 각각 실행하고 터미널을 오가며 상태와 로그를 확인한다. 포트 충돌이나 실행 순서 문제도 직접 해결해야 한다. 포폴링은 프로젝트별 실행 항목을 등록하고, 항목별 또는 전체 실행·종료를 앱에서 제어한다.

**대표 페인 포인트**

- "이 폴더가 뭐였지?" — 프로젝트 목적과 기술 스택을 다시 파악하는 데 시간이 든다.
- "어떻게 실행했더라?" — README가 없거나 오래되어 실행 방법을 다시 찾아야 한다.
- "예전엔 됐는데 왜 안 되지?" — 런타임·도구 버전이 바뀌었는데 당시 버전을 알 수 없다.
- 터미널 탭 3~5개를 열고 순서대로 명령을 입력해야 한다.
- DB가 준비되기 전에 백엔드를 띄워 실패하고 다시 실행한다.
- 이전에 띄운 서버가 포트를 잡고 있어 원인을 찾느라 시간을 쓴다.
- 작업을 끝낼 때 어떤 프로세스·컨테이너가 남았는지 확인하기 어렵다.

## 2. 목표와 범위

### 제품 목표

- 내 프로젝트 전체를 목록 하나에서 보고, 각 프로젝트가 무엇인지(설명·기술 스택·마지막 실행일) 바로 파악한다.
- 실행 방법을 설정 파일로 남겨, 시간이 지나도 버튼 하나로 다시 실행할 수 있게 한다.
- 마지막으로 성공한 실행 환경을 기록하고 현재 환경과 비교해, 실행되지 않는 원인을 찾을 근거를 준다.
- 여러 로컬 실행 항목을 한 화면에서 시작·종료하고 상태를 확인한다.
- 전체 실행 시 지정된 의존 순서를 지키고, 선행 서비스의 준비 상태를 기다린다.
- 앱이 직접 시작한 프로세스와 컨테이너만 관리해 다른 프로세스에 영향을 주지 않는다.
- 실행 로그와 기본 헬스체크 결과를 프로젝트별로 확인한다.

### MVP 범위

1. 프로젝트 폴더 등록 및 실행 항목 설정
2. 프로젝트 목록(카탈로그): 설명, 기술 스택, 태그, 마지막 실행일·결과, 실행 가능 여부 표시
3. 마지막 성공 실행 환경 기록과 현재 환경 비교
4. 실행 항목별 시작·종료 토글 및 상태 표시
5. 의존 순서가 있는 전체 실행·전체 종료
6. 포트 사용 여부 확인과 충돌 안내
7. 앱이 시작한 프로세스의 로그 조회 및 종료 정리
8. 필요한 CLI 및 Docker 데몬의 설치·연결 상태 점검
9. 등록된 Docker Compose 프로젝트의 시작(`up -d`), 상태·로그 확인, 종료(`down`)
10. URL/포트 기반 기본 헬스체크와 결과 기록
11. 원격 연결 항목: 클라우드에 배포된 API·DB 등은 켜고 끄지 않고 연결 여부만 확인
12. AI 프로젝트 검사(Gemini API): 실행 실패 원인 분석(AI-02), QA 결과 요약(AI-03)
13. Git 연동: 현재 브랜치·변경사항 표시, 전체 실행 전 최신 코드 받기(pull)

### 비목표 (MVP에서 하지 않는 것)

- 원격 서버·클라우드의 배포, 재시작, 콘솔 연동, 원격 로그 수집 (원격 항목은 연결 확인만 한다)
- 외부(앱이 시작하지 않은) 프로세스·컨테이너 종료
- 실행 명령 자동 감지·추천
- 컨테이너 이미지 빌드 관리, 볼륨 삭제, Kubernetes 지원
- 팀 간 설정 동기화 서버, 계정·로그인
- AI 프로젝트 파악(AI-01)·코드 점검(AI-04), 로컬 LLM (MVP 직후 도입)
- 개발 외 카테고리(디자인, 투자 등)의 기능
- Git 브랜치 전환(MVP 직후), 커밋·push·병합 충돌 해결, Git 로그인 처리

### AI 프로젝트 검사 (Gemini API)

포폴링의 배경(무엇이었는지 잊음, 왜 안 되는지 모름)을 AI로 더 직접 해결한다. AI는 **Gemini API**를 쓴다. 분석할 내용이 Google 서버로 전송되므로, 보내기 전에 무엇을 보내는지 보여주고 확인을 받는다.

| ID    | 기능          | 동작                                                                 | 보내는 데이터                     | 단계 |
| ----- | ----------- | ------------------------------------------------------------------ | --------------------------- | ---- |
| AI-01 | 프로젝트 파악     | 폴더를 읽고 한 줄 설명·기술 스택·실행 방법을 정리해 `about`과 `ppoling.yaml` 초안을 만들어 줌. 사용자가 확인 후 저장 | README, 설정 파일 목록, 의존성 파일 | MVP 직후 |
| AI-02 | 실행 실패 원인 분석 | 실패한 항목의 로그와 마지막 성공 환경과의 차이를 보고 원인 후보와 해결 방법 제안                     | 실패 로그 일부, 환경 비교 결과(FR-16)  | **MVP** |
| AI-03 | QA 결과 요약    | 헬스체크·전체 실행 결과를 짧은 문장으로 정리                                          | QA 결과, 실행 요약                | **MVP** |
| AI-04 | 코드 점검       | 보안 취약점, 오래된 의존성, 눈에 띄는 코드 문제를 찾아 목록으로 보여줌                         | 소스 코드(사용자가 고른 범위)          | MVP 직후 |

AI 프로젝트 검사는 기본 QA(FR-10)와 별개 기능이다. QA는 "띄운 서버가 응답하는가"만 규칙으로 판정하고, AI는 그 결과와 로그를 읽어 설명을 붙인다.

**원칙**

- API 키가 없거나 인터넷이 끊겨도 포폴링의 모든 기본 기능은 그대로 동작한다.
- API 키는 앱에 넣어 배포하지 않는다. 사용자가 앱 설정에서 자기 키를 입력하고, 키는 로그·화면·설정 파일(`ppoling.yaml`)에 평문으로 남기지 않는다.
- 보내기 전에 "이 내용이 Google로 전송됩니다"와 실제로 보낼 내용을 보여주고, 사용자가 [보내기]를 눌러야 전송한다.
- `.env` 값·응답 본문은 보내지 않고, 로그는 비밀값 가리기(AT-11)를 거친 뒤 필요한 부분만 보낸다.
- 분석은 백그라운드에서 돌리고 언제든 취소할 수 있다. 분석 중에도 실행·종료 등 다른 기능은 막지 않는다.
- AI가 만든 설정·설명은 바로 저장하지 않고 사용자가 확인한 뒤 저장한다. 실행 명령도 첫 실행 확인(§8)을 그대로 거친다.
- AI 결과는 틀릴 수 있다는 안내와 함께, 판단 근거(로그 줄, 검사 항목, 파일 위치)를 같이 보여준다.
- 키 오류·사용량 초과·네트워크 오류는 서로 구분해 안내한다.

**기본 QA와의 연계 (AI-03)**

- 통과·실패 판정은 지금처럼 규칙(FR-10)으로 한다. AI는 판정을 바꾸지 않고 결과를 읽어 설명만 붙인다.
- 보내는 데이터: 이번 QA의 검사 항목별 이름·결과·응답 코드·응답 시간·검사 시각, 같은 항목의 최근 이력(최대 5회), 전체 실행 요약(항목별 상태). URL은 호스트를 빼고 경로만 보낸다.
- 출력: 2~3문장 요약과 실패·느려진 항목 목록. 문장마다 근거가 된 검사 항목과 값(예: "API 헬스 · 503 · 14:02")을 붙인다.
- 위치: QA 결과 화면(9장 6번) 아래 [AI 요약] 버튼. 누를 때만 분석하고, 결과는 AI 검사 화면의 분석 기록에도 남긴다.
- 모두 통과하고 이전과 차이가 없으면 API를 부르지 않고 "모든 검사를 통과했어요"만 보여준다.
- 실패한 검사 항목에는 [원인 분석] 버튼을 두어, 그 URL을 맡은 실행 항목의 로그와 함께 AI-02로 넘긴다.

**모델과 비용**

- 모델: 응답이 빠르고 저렴한 Gemini Flash 계열을 기본으로 한다. 구체 모델 이름은 착수 시점의 공개 모델을 확인해 정한다.
- 무료 등급은 사용량 제한이 있고, 입력 데이터가 Google 서비스 개선에 쓰일 수 있다. 착수 전에 최신 약관과 제한을 확인하고, 그 내용을 키 입력 화면에 안내한다.
- AI 호출은 `LlmClient` 인터페이스 뒤에 두어, MVP 직후 로컬 LLM(Ollama 등) 구현을 추가할 수 있게 한다.

**완료 기준(초안)**

- API 키가 없으면 AI 버튼 자리에 "API 키 필요"와 [키 입력]만 보이고, 다른 기능은 영향이 없다.
- 사용자가 [보내기]를 누르기 전에는 아무것도 전송되지 않고, 보낸 내용에 `.env` 값·API 키가 없다.
- AI-02는 실패 로그와 환경 비교 결과를 근거로 원인 후보를 하나 이상 제시한다.
- AI-03 요약의 문장마다 근거(검사 항목·값)가 붙고, AI 요약을 받아도 QA 통과·실패 판정은 바뀌지 않는다.
- AI가 제안한 설정은 사용자가 [적용]을 누르기 전에는 `ppoling.yaml`에 쓰이지 않는다(AI-01, MVP 직후).

### MVP 직후: 실행 프로필

같은 프로젝트를 상황에 따라 다르게 띄우는 기능. 예를 들어 평소엔 DB를 로컬 Docker로 띄우고, 가끔은 배포된 API에 붙여 프론트만 실행한다.

```yaml
profiles:
  local:  { db: compose, api: process, web: process }
  remote: { db: remote,  api: remote,  web: process }
```

- 대시보드 상단에서 프로필을 고르면 항목 구성과 환경변수(예: `VITE_API_URL`)가 함께 바뀐다.
- 프로필이 없으면 지금처럼 기본 구성 하나로 동작한다.

### MVP 이후 후보

- Git 브랜치 전환 (MVP 직후. 커밋하지 않은 변경이 있으면 막는다)
- 앱 내 웹뷰·터미널
- 프로젝트 폴더 자동 감지 및 실행 설정 추천 (`package.json` scripts, `docker-compose.yml` 등)
- 실행 프로필은 'MVP 직후' 참조

각 후보는 운영체제, 보안, 오류 복구 범위와 구현 비용을 확인한 뒤 별도 우선순위로 확정한다.

| 용어                    | 의미                                                    |
| --------------------- | ----------------------------------------------------- |

| 실행 항목(Service)        | 프로젝트 안에서 독립적으로 시작·종료되는 단위. `process`, `compose`, `remote` 유형  |
| 원격 연결(remote)         | 내 컴퓨터가 아닌 곳(클라우드·배포 서버)에서 도는 항목. 포폴링은 켜고 끄지 않고 연결 여부만 확인한다 |
| 준비 조건(Readiness)      | 실행 항목이 "사용 가능"하다고 판단하는 기준 (포트 열림, HTTP 응답, 로그 패턴 등)   |
| 헬스체크(QA)              | 사용자가 요청할 때 실행하는 점검. 결과와 근거를 기록                        |
| 소유권                   | 앱이 해당 프로세스·컨테이너를 직접 시작했다는 검증 가능한 기록                   |
| 실행 기록(Runtime record) | PID, 시작 시각, 명령, Compose 프로젝트명 등 앱 데이터 영역에 저장하는 런타임 정보 |


## 4. 사용자와 주요 흐름

**대상 사용자:** 여러 서비스를 동시에 실행하는 학생 및 개발자.

**페르소나 예시**

- **팀 프로젝트 학생:** Spring 백엔드 + React 프론트 + MySQL(Docker)을 매번 띄운다. 터미널 사용이 익숙하지 않은 팀원도 있다.
- **사이드 프로젝트 개발자:** 프로젝트 여러 개를 오가며 작업한다. 이전 프로젝트 서버가 남아 포트 충돌이 자주 난다.
- **포트폴리오를 정리하는 취업 준비생:** 1~2년 전 과제·프로젝트를 면접 전에 다시 띄워 시연해야 하는데, 실행 방법도 기억나지 않고 버전이 바뀌어 실행되지 않는다.

**대표 흐름**

1. 사용자가 프로젝트 폴더를 등록한다. 폴더에 `ppoling.yaml`이 있으면 읽고, 없으면 앱에서 새로 만든다.
2. 앱이 실행 명령, 작업 디렉터리, 포트, 준비 확인 방법 및 의존 항목을 보여준다.
3. 환경 점검으로 필요한 도구와 버전을 확인하고, 문제 해결 안내를 제공한다.
4. 사용자가 항목별로 실행하거나 전체 실행을 선택한다.
5. 앱이 프로세스와 Compose 서비스를 의존 순서대로 시작하고 준비 조건을 기다리며 상태와 로그를 표시한다.
6. 사용자가 전체 또는 개별 종료를 실행한다. 앱은 자신이 시작한 프로세스와 등록된 Compose 프로젝트만 정리한다.
7. 사용자가 헬스체크를 실행해 통과/실패, 검사 시각, 응답 코드 등 근거를 확인한다.
8. 앱 종료 시 실행 중인 항목이 있으면  "종료 / 취소"를 묻는다.

| ----- | ----------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| FR-01 | 프로젝트 등록           | 필수   | 로컬 폴더 경로와 프로젝트 이름을 등록·수정·삭제한다. 경로 접근 오류를 안내한다. 삭제는 앱 목록에서만 제거하며 폴더·설정 파일은 지우지 않는다.                                                               |

| FR-04 | 전체 실행             | 필수   | 의존 관계 위상 정렬 순서로 실행하고 준비 대기 후 다음 항목으로 넘어간다. 정책은 §6 참조.                                                                                            |

| FR-15 | 프로젝트 메모           | 필수   | 설명, 기술 스택, 링크(저장소·배포 주소), 자유 메모를 `ppoling.yaml`의 `about`에 저장한다. 등록 시 README 첫 문단과 Git 원격 주소를 기본값으로 채워 준다(사용자가 수정 가능).                            |
| FR-16 | 실행 환경 기록·비교       | 필수   | 전체 실행이 성공하면 그때의 CLI 버전(`requires` 대상), Docker 이미지 태그, Git 커밋, 실행 일시를 "마지막 성공 환경"으로 저장한다. 다음 실행 전과 실패 시 현재 환경과 비교해 달라진 항목을 보여준다(예: Node 18 → 22). |
| FR-17 | 오래된 프로젝트 점검       | 권장   | 일정 기간(기본 90일) 실행하지 않은 프로젝트는 "오래됨"으로 표시하고, 버튼 하나로 환경 점검 + 전체 실행 + 기본 QA를 차례로 실행해 지금도 실행되는지 확인한다.                                                  |
| FR-18 | 원격 연결 항목         | 필수   | `type: remote` 항목은 시작·종료하지 않고 `http` 또는 `port`(host 지정) 준비 조건으로 연결 여부만 확인해 `연결됨`/`연결 안 됨`으로 표시한다. 의존 순서에는 포함되며, 전체 종료에서는 건너뛴다. 주소는 `ppoling.yaml`에 적고, 토큰·비밀번호 같은 비밀값은 `.env`로만 참조한다. |
| FR-19 | Git 연동         | 필수   | 프로젝트 폴더가 Git 저장소면 대시보드에 현재 브랜치, 커밋하지 않은 변경 파일 수, 원격보다 뒤처진 커밋 수를 표시한다. 전체 실행 전에 `git pull --ff-only`로 최신 코드를 받는다(`git.pullBeforeRun`, 기본 켬). 정책은 §6 참조. Git이 없거나 저장소가 아니면 표시를 숨기고 실행에는 영향이 없다. |


## 6. 실행·종료 정책

### 전체 실행

- 시작 전 Git pull(FR-19, `git.pullBeforeRun`이 켜져 있을 때): fast-forward만 한다. 커밋하지 않은 변경이 있거나, fast-forward가 안 되거나, 인증·네트워크 오류면 pull을 건너뛰고 이유를 표시한 뒤 지금 코드로 실행을 계속한다. stash·reset·merge는 하지 않는다. pull로 `ppoling.yaml`이 바뀌었으면 바뀐 실행 명령을 보여주고 확인받은 뒤 진행한다.
- 의존 그래프를 위상 정렬한다. 순환 의존은 설정 검증 단계에서 차단한다.
- 이미 `준비 완료`인 항목은 건너뛴다. `실행 중`(준비 조건 미충족)은 준비를 계속 기다린다.
- 의존이 없는 항목끼리는 병렬로 시작할 수 있다. (MVP는 순차 시작도 허용, 병렬은 검증 후 결정)
- 한 항목이 실패하거나 준비 제한 시간을 넘기면 **그 항목에 의존하는 항목은 시작하지 않고** 나머지 독립 항목은 계속 진행한다. 이미 시작한 항목은 자동 종료하지 않는다.
- 원격 연결 항목은 시작하지 않고 연결 확인만 한다. 연결되면 다음 항목으로 넘어가고, 연결이 안 되면 실패와 같이 처리한다(그 항목에 의존하는 항목은 시작하지 않음).
- 결과 요약: 성공 / 실패 / 건너뜀 항목 목록을 표시한다.

### 전체 종료

- 의존 역순으로 종료한다.
- 항목별로 정상 종료 신호 → `stopTimeout`(기본 10초) 대기 → 여전히 살아 있으면 강제 종료한다.
- 강제 종료한 항목은 결과에 표시한다.
- 원격 연결 항목은 종료하지 않고 건너뛴다.

### 준비 조건 유형


| 유형                | 판정                                   |
| ----------------- | ------------------------------------ |
| `port`            | 지정 포트에 TCP 연결 성공 (원격은 `host` 지정)   |
| `http`            | 지정 URL이 기대 상태 코드(기본 2xx\~3xx) 응답     |
| `log`             | 출력에 지정 정규식이 나타남 (예: `Started .* in`) |
| `compose-healthy` | Compose 서비스의 healthcheck가 `healthy`  |
| `none`            | 프로세스가 시작되면 즉시 준비 완료                  |


모든 조건에 `timeout`(기본 60초)과 `interval`(기본 1초)을 둔다.

### 상태 전이

```
중지 ──시작──▶ 시작 중 ──프로세스 생성──▶ 실행 중 ──준비 조건 충족──▶ 준비 완료
  ▲              │                          │                         │
  │              └──생성 실패──▶ 실패 ◀──비정상 종료/준비 시간 초과──┘
  │                                          │
  └──────── 종료 완료 ◀── 종료 중 ◀──종료 요청──(실행 중·준비 완료)
```

- `연결됨` / `연결 안 됨`: 원격 연결 항목 전용 상태. 시작·중지 대신 [다시 확인]만 제공한다.
- `포트 사용 중`: 시작 전 포트 점검에서 감지. 시작하지 않고, 포트를 쓰는 내 프로젝트·항목 또는 외부 프로그램을 함께 표시한다.
- `확인 불가`: 앱 재시작 후 소유권을 검증할 수 없는 실행 기록.
- 실행 중 프로세스가 스스로 종료되면 종료 코드 0은 `중지`, 그 외는 `실패`로 표시한다.
- `실패` 상태에서도 다시 시작할 수 있다(실패 → 시작 중).

## 7. 설정 파일

### 원칙

- 사람이 읽고 편집할 수 있는 프로젝트별 설정 파일 `ppoling.yaml`을 프로젝트 루트에 둔다. Git으로 공유할 수 있다.
- 실행 명령과 인자는 배열로 구조화해 저장하고, 셸 문자열로 조합하지 않는다. 셸 기능(파이프, `&&`)은 지원하지 않는다(`shell: true` 없음). 필요하면 스크립트 파일을 만들어 그 파일을 명령으로 등록한다.
- 비밀값은 설정 파일에 쓰지 않는다. MVP에서는 `.env` 파일 참조만 허용하고(키체인 참조는 MVP 이후), 로그 출력 시 마스킹한다.
- PID 등 런타임 기록은 프로젝트 폴더가 아닌 사용자 앱 데이터 영역에 둔다.
- 설정에 `version` 필드를 두어 스키마 변경에 대비한다.

**형식:** YAML로 확정했다(주석 가능, 사람이 편집하기 쉬움). 발표자료의 Markdown 저장 안은 구조 검증이 어려워 쓰지 않는다.

### 스키마 예시 (초안)

```yaml
version: 1
name: my-team-project
about:              # 나중에 다시 봐도 뭔지 알 수 있게
  summary: 동아리 행사 예약 웹서비스 (2025 캡스톤)
  stack: [Spring Boot, React, MySQL]
  links:
    repo: https://github.com/example/my-team-project
  memo: 관리자 계정은 .env 의 ADMIN_* 참고
requires:            # 환경 점검 대상
  - cli: node
    version: ">=20"
  - cli: java
    version: ">=17"
  - docker: true
git:
  pullBeforeRun: true  # 전체 실행 전 fast-forward pull (기본 켬)

services:
  - id: db
    type: compose
    file: ./docker-compose.yml
    services: [mysql]        # 비우면 파일 전체
    ready:
      type: compose-healthy
      timeout: 90

  - id: api
    type: process
    cwd: ./backend
    command: ["./gradlew", "bootRun"]
    env:
      SPRING_PROFILES_ACTIVE: local
    envFile: ./backend/.env
    ports: [8080]
    dependsOn: [db]
    ready:
      type: http
      url: http://localhost:8080/actuator/health
      timeout: 120
    stopTimeout: 15

  - id: web
    type: process
    cwd: ./frontend
    command: ["npm", "run", "dev"]
    ports: [5173]
    dependsOn: [api]
    ready:
      type: port
      port: 5173

  - id: storage          # 원격 연결: 켜고 끄지 않고 연결만 확인
    type: remote
    ready:
      type: http
      url: https://storage.my-team.dev/health
      timeout: 10

checks:              # 기본 QA
  - name: 프론트 메인
    url: http://localhost:5173
  - name: API 헬스
    url: http://localhost:8080/actuator/health
    expectStatus: 200
```

### 앱 데이터 저장 위치


| OS      | 경로                                        |
| ------- | ----------------------------------------- |
| macOS   | `~/Library/Application Support/POPOL-ing/` |
| Windows | `%APPDATA%\POPOL-ing\`                     |


저장 내용: 등록 프로젝트 목록, 실행 기록, 로그 파일, QA 결과 이력, 앱 설정. AI 분석 기록(보낸 내용 요약·결과·근거·사용 모델·시각). Gemini API 키는 디스크에 평문으로 두지 않고 화면·로그에는 가린다. 저장 방식(OS 보안 저장소 등)은 §16의 2번에서 3주차 시작 전에 정한다.

## 8. 안전성과 오류 처리

- **프로세스 소유권:** 시작 시 PID와 함께 프로세스 시작 시각, 실행 파일 경로, 명령 인자, 앱 실행 ID를 기록한다. 재검증 시 이 값이 모두 일치해야 소유로 판정한다. 포트 번호나 PID 하나만으로 종료하지 않는다.
- **Compose 소유권:** `docker compose -p ppoling-<프로젝트ID>`로 프로젝트명을 고정해, 같은 compose 파일을 사용자가 직접 띄운 경우와 구분한다.
- **종료 절차:** 정상 종료 신호와 제한 시간을 먼저 적용하고, 실패 시에만 강제 종료한다. 강제 종료 대상과 결과를 사용자에게 보여준다.
- **포트 충돌:** 포폴링이 띄운 내 프로젝트 항목이 포트를 쓰고 있으면 그 항목만 중지할 수 있다(전체 종료와 같은 종료 절차). 외부 프로그램은 경고만 제공하고 종료하지 않는다.
- **명령 실행:** 작업 폴더가 프로젝트 폴더 하위인지 확인한다. 인자·환경변수는 배열로 전달해 셸 해석을 피한다.
- **오류 안내:** 실행 명령 실패, 준비 대기 시간 초과, 포트 충돌, CLI 미설치, Docker 데몬 미실행, 권한 오류, 설정 검증 오류를 서로 구분해 표시하고 각각 다음 조치를 안내한다.
- **앱 비정상 종료:** 다음 실행에서 이전 소유권 정보를 검증한다. 검증 불가 대상은 자동 종료하지 않는다.
- **신뢰하지 않는 설정:** 다른 사람이 만든 `ppoling.yaml`을 처음 열 때 실행될 명령 목록을 보여주고 사용자 확인 후 실행한다.
- **Git pull:** `--ff-only`로만 받아 사용자의 커밋하지 않은 변경·로컬 커밋을 덮어쓰지 않는다. 인증 창을 띄우지 않게 `GIT_TERMINAL_PROMPT=0`으로 실행하고 제한 시간(초안: 30초)을 둔다. 실패해도 실행은 막지 않는다.
- **AI 기능:** 실행·종료 같은 기본 경로에 넣지 않는다. Gemini API로 보내기 전에 보낼 내용을 보여주고 확인받으며, `.env` 값·API 키는 보내지 않는다. §2 'AI 프로젝트 검사'의 원칙을 따른다.

## 9. 화면 구성 초안

1. **첫 화면(카테고리 선택):** 카테고리 카드(MVP는 개발). 앱을 열면 항상 이 화면부터 보여준다
2. **개발 홈(프로젝트 카탈로그):** 프로젝트 카드(이름·한 줄 설명·스택 태그·마지막 실행일·결과·실행 중 n개·오래됨 표시), 검색·필터·정렬, 카드에서 바로 전체 실행, 프로젝트 추가
3. **프로젝트 대시보드:** 프로젝트 소개(설명·스택·링크·메모), 마지막 성공 환경과 현재 환경 차이, 환경 상태 배지, Git 브랜치·변경 파일 수·뒤처진 커밋 수, 전체 실행·종료, 실행 항목 카드(상태·포트·준비 조건·토글), 의존 순서 표시
4. **항목 상세:** 실행 설정, 시작·종료, 준비 상태, 실시간 로그(검색·자동 스크롤 고정·복사)
5. **환경 점검:** 필요한 CLI, 감지 버전, 문제 및 해결 안내(설치 링크 등)
6. **QA 결과:** 검사 항목별 통과·실패, 응답 코드·시간, 검사 시각, 이력, [AI 요약]·실패 항목의 [원인 분석] 버튼
7. **프로젝트 설정:** 경로, 실행 항목 편집, 의존 순서, 헬스체크 설정, 설정 파일 열기
8. **AI 검사:** API 키 상태·[키 입력], 실행 실패 원인 분석·QA 결과 요약 카드, 분석 기록 (프로젝트 파악·코드 점검 카드는 MVP 직후)

상태 표시 색·아이콘은 색만으로 구분하지 않고 텍스트 라벨을 함께 쓴다.

## 10. 기술 구조

### 계층

```
UI
  ├─ 카테고리 선택 화면
  ├─ 공통 코어 (카탈로그·항목 소개·태그·검색 — 개발 카테고리에 필요한 만큼만)
  └─ 개발 카테고리 모듈
       └─ 애플리케이션 계층 (전체 실행 오케스트레이터, 상태 머신, 설정 검증)
       ├─ ProcessRunner (OS별 구현: macOS / Windows)
       ├─ ComposeAdapter (docker compose CLI 호출)
       ├─ GitAdapter (git CLI 호출: status, pull --ff-only)
       ├─ PortProbe / ReadinessChecker / HealthChecker
       ├─ LogStore (회전 파일 + 메모리 버퍼)
       └─ RuntimeStore (실행 기록·소유권)
```

- 코드는 기능 단위 모듈(`runner`·`project`·`checks`·`compose`·`catalog`·`qa`·`ai`)로 나누고, 모듈끼리는 `core/`의 인터페이스·이벤트로만 주고받는다. 대시보드처럼 여러 기능이 모이는 화면은 각 모듈의 컴포넌트를 끼워 조립한다. 폴더별 담당과 계약은 `docs/포폴링_역할분담.md`.
- UI와 프로세스 제어 계층을 분리한다. 오케스트레이터는 UI 없이 테스트할 수 있어야 한다.
- 카테고리 모듈은 서로 의존하지 않는다. 다른 카테고리를 추가할 때 개발 모듈을 고치지 않아도 되게 한다.
- 앱 데이터의 프로젝트 목록에 `category` 필드를 둔다(MVP 값은 `dev` 하나).
- AI 호출은 `LlmClient` 인터페이스로 격리하고(MVP 구현은 Gemini API), 기본 기능이 AI 없이 동작하도록 한다. 로컬 LLM은 MVP 직후 같은 인터페이스의 구현으로 추가한다.

| 과제            | macOS                                              | Windows                                                    |
| ------------- | -------------------------------------------------- | ---------------------------------------------------------- |
| 프로세스 트리 종료    | 새 프로세스 그룹으로 시작 → 그룹에 `SIGTERM` → 제한 시간 후 `SIGKILL` | Job Object에 할당 → 정상 종료 시도(`CTRL_BREAK` 등) → 제한 시간 후 Job 종료 |
| 포트 점유 확인      | TCP 연결 시도 + `lsof`로 점유 프로세스 조회                     | TCP 연결 시도 + `netstat -ano`/API로 조회                         |
| PATH 문제       | GUI 앱은 로그인 셸 PATH를 못 받는 경우가 있어 셸 환경 로드 방식 검증       | `npm` 등이 `.cmd`라 실행 파일 해석 방식 검증                            |
| 프로세스 시작 시각 조회 | `ps -o lstart` 또는 `sysctl`                         | `GetProcessTimes`                                          |


### 기술 스택

**Flutter 데스크톱**으로 확정한다. UI와 프로세스 제어를 하나의 Dart 코드베이스로 만든다.

- Dart 기본 `Process`로 시작·입출력·종료 코드를 다룬다.
- OS 기능이 더 필요한 부분(Windows Job Object·콘솔 종료 신호, 프로세스 시작 시각 조회)은 OS별 구현 안에서 **Dart FFI**로 Win32 API를 부르거나, `ps`·`lsof`·`netstat` 같은 명령을 호출해 처리한다.
- 위 "OS별 구현 메모"의 과제는 Flutter 안에서 **어떻게 구현할지** 확인하는 검증이다. 스택을 바꿀지 판단하는 단계는 두지 않는다.

## 11. 비기능 요구사항

- 상태 변화는 1초 이내에 화면에 반영한다.
- 준비 확인과 헬스체크에는 설정 가능한 제한 시간이 있다.
- 앱이 실행하지 않은 프로세스를 종료하는 코드 경로가 없어야 한다.
- 설정이 잘못되거나 CLI가 없어도 앱이 종료되지 않고 다음 조치를 안내한다.
- 로그에 비밀값을 기록하지 않는다. 항목별 로그는 파일 크기 기준으로 회전한다(초안: 10MB × 3개). 화면 버퍼는 최근 5,000줄.
- 실행 항목 20개, 로그 초당 1,000줄에서도 UI가 멈추지 않는다.
- 앱 기동 후 대시보드 표시까지 3초 이내(초안 수치, 검증 후 조정).

## 16. 착수 전 남은 결정

1. macOS·Windows 최소 지원 버전 (제안: macOS 13+, Windows 10 22H2+)
2. Gemini API 키 저장 방식: OS 보안 저장소(키체인 등)를 쓸지 — **3주차 시작 전**. 프로젝트 비밀값은 MVP에서 `.env` 참조만 지원한다
3. 두 번째로 만들 카테고리와 시기 (디자인 / 투자 / 기타)
4. 투자 카테고리의 범위: 매매 기록·투자 근거를 정리하는 **기록형 포트폴리오**인가, 증권사 연동으로 자산을 추적하는 **자산 관리형**인가? (자산 관리형은 금융 데이터 연동·보안·규제 검토가 필요해 규모가 크게 달라짐)
5. 카테고리 간 묶어 보기(예: 한 사람의 개발+디자인 포트폴리오를 하나로 내보내기)가 필요한가?
6. Gemini 기본 모델과 무료·유료 등급 — **3주차 시작 전** (데이터가 서비스 개선에 쓰이는지에 따라 팀 프로젝트 코드·로그를 보내도 되는지가 달라짐)
7. MVP 직후 로컬 LLM 런타임: 앱에 llama.cpp를 내장할지, 사용자가 설치한 Ollama에 연결할지

**결정 완료:** 기술 스택 Flutter 데스크톱, 첫 화면 카테고리 선택 구조, MVP는 개발 카테고리만, 지원 OS(macOS·Windows), Docker Compose MVP 포함, AI 프로젝트 검사는 Gemini API로 MVP에 AI-02·03 포함(로컬 LLM은 MVP 직후), 포트 충돌 시 내 프로젝트 항목은 중지 가능, 원격 서버·DB는 연결 확인만(MVP), 실행 프로필은 MVP 직후, 실행 명령은 사용자 직접 등록(자동 감지는 후속), 설정 파일은 YAML(`ppoling.yaml`), `shell: true`는 지원하지 않음, 6주 안에는 발표용 빌드만 만든다(서명·자동 업데이트·일반 배포는 범위 밖).
